# 跨会话感知修复：方案与实现

跨会话感知链路自光谱核心 0.3.3 起提供。0.3.4 移除专用身份规则；角色称呼由 AstrBot 当前人设决定。

## 目标

让不同窗口里的AI保持同一个人的经历与记忆。提起另一段交往时，它可以回忆当时的人物、原话和时间；回忆进入它的上下文，是否说出来由它决定。此次修复不使用向量模型，也不增加专用的记忆评分模型调用。

## 参考资料和采用范围

- [微软：事件溯源模式](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing)。采用事件保留、关联更新、从历史事件读取状态和补充更正的原则；继续使用现有SQLite与锁，不引入消息队列或完整CQRS平台。
- [LangMem：记忆概念](https://github.com/langchain-ai/langmem/blob/main/docs/docs/concepts/conceptual_guide.md)。采用经历与事实认知分工；会话历史和个人持久记忆分别读取。具体人物边界和表达选择是本插件的实现设计，不是资料对模型效果的保证。

## 原因与修复

| 原有断点 | 本次实现 |
| --- | --- |
| 同一人自己经历过的事实被当前会话受众过滤 | 保留原背景筛选，另行补充标明来源的自我经历；“我知道”与“当前对象参与过或知道”分开 |
| 睡醒换生活段后旧物理事件消失 | 未结束经历跨段保留；结束经历按话题召回，日期不变 |
| 来源认知没有对应更新通道 | 增加knowledge事件，引用真实received消息编号，关联原事件；由原调用模型提取，代码校验来源与提交 |
| 后续确认覆盖后无法看到原发生时间 | 沿related_id还原事件链，分别显示发生、得知、处理的时间 |
| 提起其他会话时只能依靠人物名字 | 人物或话题匹配其他会话原话，召回邻接片段时限定同一来源会话 |
| 旧疑问被当成当前仍未知 | 输入明确区分真实原话、当时疑问和后续已记录进展；本次历史记录补充来源确认和奶茶处理事件 |

## 数据流

1. 原始received、delivered消息保存在现有entries表，人物与会话标识不变。
2. 已发生身体行动进入physical事件；真实说出口的承诺进入commitment事件；从实际收到消息得知的来源或进展进入knowledge事件。
3. 更新以relatedId关联原事件，不删除旧事件。承诺仍要求在原会话或实际跨会话投递回执中更新。
4. 前台回复、后台生活推进与状态压缩读取相同的经历上下文。当前背景、自我经历、他会话回忆分段显示。
5. 人物或话题召回只读取真实收发消息；日记猜测不能充当他人原话。每段保留来源会话、人物、时间与原始消息编号。
6. 世界版本包含全部共享事件，生成期间的新更新仍触发原有重新读取检查。

## 设置与行为

- 保留现有指令、配置字段和管理页面。
- “跨会话引用”开关控制自动召回其他会话原话；片段数量、篇幅沿用原文回忆的限制。
- 此处不使用向量；其他已存在功能的向量设置不作修改。
- 其他会话回忆是AI自己的记忆输入。是否提起和表达多少由AI决定，不由代码替它生成固定回复。群聊和私聊中的当前人物资料仍按原有规则构建；不能把新增的回忆通道理解成对输出保密的硬性保证。
- 接口保留兼容：旧physical/commitment事件无需迁移，数据库没有新增列或删除聊天表。knowledge只使用既有字段。

## 历史记录更正

已有实例若包含历史歧义，应先备份，再根据该实例的原始记录补充后续事件和事实摘要。原始聊天、提问和日记保留，重复更正不应重复添加事件。发布源码不附带个人实例的历史更正脚本，也不会自动导入示例记忆。

## 验证

必要检查覆盖跨生活段保留、后续来源确认、人物与话题召回、片段人物边界、长输入末尾话题、伪造来源不提交，以及原有前后台世界版本检查。另在临时数据库回放已有实例的记录，核对事件链及上下文，并比较原始消息指纹。未调用模型或发送QQ测试消息；实际措辞效果需部署后观察真实对话。
